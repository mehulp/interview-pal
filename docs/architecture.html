InterviewPal architecture

A mock-interview app that runs entirely in the browser. This page shows how it is put together, what talks to what, where it can fail, and what would change if it had to serve many people.

Who talks to whom

There is no backend. The browser holds the app, the data and the interface, and reaches outside only when a feature needs it. About 5,400 lines of plain HTML, CSS and JavaScript, with no framework and no build step, plus unit tests for the pure logic.

Three layers of code

The rules that matter live in small pure modules. The messy browser and network work sits behind adapters. The screens call both.

The interview is a small state machine

Each question moves through the same few phases. Two details keep it safe: a short finishing phase while the app waits for the last spoken words, and a token that makes late timers and late speech results harmless.

The finishing phase

Chrome delivers the last words a moment after you stop. Next waits up to about 1.5 seconds so nothing is cut off, and blocks double clicks while it waits.

The epoch token

Every question run gets an id. If you skip, end the session or the timer fires, older waiting code sees a stale id and quietly stops. The recogniser uses the same idea, so an old timeout cannot end a newer listening session.

Data model and storage

Two shapes of data, kept apart on purpose. A history record is a copy of what happened, so editing or deleting a question later never rewrites the past.

Patterns worth knowing the names of

Strategy

avatar.js draws the face as an SVG, photo frames or video clips behind one interface, setState. New kinds of face need no change elsewhere.

Adapter with graceful degradation

speech.js, storage.js and claude.js hide browser quirks and fall back (typing, defaults, the drawn face) when something is missing.

State machine plus epoch token

Phases are explicit, and a run id lets late async work detect that it is out of date.

Pure core, thin shell

Rules live in modules with no page code, so they can be tested in Node without a browser. npm test runs 62 tests, and a GitHub Action runs them on every push.

Lazy loading

The Claude client loads by dynamic import, and the Word and PDF libraries load on demand. Practice mode never loads the API code.

Migrate on read

The old single question list becomes a set the first time the new version runs. No separate migration step.

Validate before mutating

An import is parsed and checked completely, then merged. A bad file cannot damage saved data.

Snapshot

A session record copies what it needs, so history stays correct when questions change.

Derive, do not store twice

The progress view (trend, streak, weak topics) is worked out from the saved history each time it is opened. There is no second copy to keep in step.

Safe output

Anything from your notes or from the AI is set as text, never as HTML, so it cannot inject markup.

Scaling is not a concern, because each user runs their own copy. What grows with use is Anthropic token cost (a few cents per Coach session) and, if images were hosted, bandwidth.

Describing it in a system design interview

  1. Requirements. Practise interviews daily, private, cheap, laptop and phone, and typing must always work.
  2. Key constraint. A single user, so no backend is needed. That removes authentication, scaling and data protection as problems.
  3. Boundaries. Say exactly what leaves the device (Coach requests, voice audio) and why.
  4. Failure handling. For each outside dependency (speech, the API, media, storage), say what the fallback is.
  5. Evolution. Name the first thing that breaks with growth (the key in the browser, no device sync) and the fix (a proxy and a database).

Test yourself

Answer out loud first, then open the answer.

Where is the trust boundary, and what crosses it?

The browser. Your notes, answers and history stay inside. Two things cross: your answer to Anthropic in Coach mode, and your voice to Google through Chrome's recogniser.

Why is the parsing and set logic free of browser code?

So it can be tested with plain Node scripts, and so the rules are in one place that the screens call. Browser quirks stay in the adapters.

What problem does the run id token solve?

Late async results. If you skip, end the session or a timer fires, older waiting code sees a stale id and stops, so it cannot change the screen or save an old answer.

Why does a history record copy the question text?

History must show what happened, not what the question says today. A copy is unaffected when you edit, move or delete the question.

What two things must change before many people could use this?

The API key must move to a server, with login and rate limits, and the data needs a database so it follows people between devices.

Why does Next wait up to 1.5 seconds?

The recogniser delivers the last words after you stop talking. Reading the answer box immediately would cut them off. The wait is capped so it can never hang.
